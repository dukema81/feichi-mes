# 飞驰MES系统建设方案

> 版本 ｜ V1.0 · 2026 年 10 月 · 飞驰精密制造（苏州）有限公司 制造信息化项目组

## 1 项目概述

### 1.1 建设背景

飞驰精密制造（苏州）有限公司现有 4 个车间、7 条产线、25 台关键设备、25 个工位，年产智能网关、运动控制器等整机 30 余万台。当前生产现场存在四个突出矛盾：

- **计划与现场两张皮**：排产结果停留在 Excel 与微信群，工单下到班组后进度靠口头反馈，计划员无法判断某张工单"卡在哪道工序"。
- **报工与产出对不上账**：按工序逐条报工，同一批产出在多道工序被重复计数，月度产量与入库量长期存在 20% 以上偏差，OEE 无从计算。
- **质量数据散落**：首件、巡检、完工检分别记录在三份纸质表单，缺陷没有统一编码，无法做帕累托与过程能力分析，批次出问题只能全量召回。
- **设备与保养脱节**：设备停机原因不记录、不汇总，保养计划靠人盯，故障停机与保养到期互相掩盖。

公司已上线飞鹰 CRM（客户与销售）与飞泉 SCM（采购与库存），两条主线的数据已经打通到"接单"和"到料"，缺少的正是中间的**制造执行层**——把销售订单变成工单、把料变成整机、把过程变成可追溯的数据。

### 1.2 建设目标

| 目标 | 度量口径 | 现状 | 目标值 |
| --- | --- | --- | --- |
| 工单全过程在线 | 在制工单系统内覆盖率 | 约 40% | 100% |
| 产量口径统一 | 报表产量与入库量偏差 | 20%+ | ≤ 2% |
| 设备综合效率可见 | 有 OEE 数据的设备占比 | 0 | 100%（25/25） |
| 质量问题可定位 | 批次追溯响应时间 | 半天以上 | 秒级（单批次 < 1 秒） |
| 保养按期率 | 保养工单按期完成率 | 约 60% | ≥ 90% |
| 系统对接 | 与 ERP / WMS / CRM 打通 | 人工导表 | 三通道 API |

### 1.3 建设范围

**本期包含**

- 主数据：车间、产线、工位、班组、物料、BOM、工艺路线、设备台账、不良代码。
- 生产执行：排产计划、工单状态机、派工、齐套与发料、工序报工、完工入库、生产看板、安灯呼叫。
- 质量：首件 / 巡检 / 完工检、不良登记与处置、Cpk 过程能力、缺陷帕累托、质量总览。
- 追溯：批次主档、批次父子链、正反向追溯树、报工—检验—入库全链路。
- 设备：设备台账、状态机与停机原因、点检、保养计划与保养工单、OEE / MTBF / MTTR。
- 库存：按批次的物料台账、成品入库、库存汇总。
- 报表：产量与计划、OEE 三率、质量趋势、产线负荷、设备排名、停机 TOP、物料消耗 TOP、CSV 导出。
- 集成：API Key、Webhook（HMAC 签名 + 退避重投）、增量同步、外部 ID 映射、OpenAPI 3.0 规范。

**本期不含**（后续迭代）

- 与设备的直连采集（OPC UA / Modbus），本期以点检 + 报工 + 状态登记替代。
- APS 高级排程算法，本期按产能负荷给出建议而不反解最优解。
- 供应商协同门户、SPC 实时控制图、AI 缺陷视觉识别。

### 1.4 术语约定

| 术语 | 含义 |
| --- | --- |
| 工单（WO） | 一次生产指令，对应"某物料 × 某数量 × 某产线 × 某计划期" |
| 工序（Operation） | 工单在工艺路线上的一个执行步骤，按 seq 升序执行 |
| 报工（Report） | 工序级的产出与工时申报，含合格数、不良数、实际工时 |
| 首件（FAI） | 开工后首件检验，零缺陷才放行批量生产 |
| 完工检（FQC） | 完工后抽检，结论决定是否可入库 |
| 齐套率（Kit Rate） | 用料可用量（现有库存 + 已发料）满足需求的比例 |
| OEE | 设备综合效率 = 可用率 × 性能率 × 质量率 |
| 批次（Batch） | 可追溯的最小产出单位，批次之间有父子关系 |
| 安灯（Andon） | 现场异常呼叫，按产线 / 工位 / 类型 / 级别登记与关闭 |

## 3 总体架构

### 3.1 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 后端 | Python 3 标准库 `http.server` | 工厂内网环境无外网、无法安装依赖；标准库即可承载 200 人以内并发 |
| 数据库 | SQLite（WAL 模式） | 单文件、零运维、可整库拷贝备份；`busy_timeout=20s` + 全局写锁串行化 |
| 前端 | 原生 HTML / CSS / JavaScript | 免构建、免 CDN；内网浏览器（Chrome/Edge 88+）直接打开 |
| 集成 | REST + Webhook + 增量同步 | 覆盖"我调他""他调我""批量对账"三种真实对接需求 |
| 部署 | 单进程 + 反向代理 | 一条 `python backend/server.py` 启动，systemd / 计划任务托管 |

**为什么要零依赖**：MES 是车间系统，服务器往往是产线上的工控机或老旧虚拟机，Python 版本参差（3.8~3.13），无 pip 源、无 Docker。任何三方包都会变成长期运维负担。本项目全部能力用标准库实现，单文件二进制之外零外部依赖，拷贝目录即可运行。

### 3.2 逻辑架构

```
┌──────────────────────────── 浏览器（内网 Chrome / Edge） ────────────────────────────┐
│  index.html  登录页  14 个功能页（hash 路由）  单文件离线 DEMO                        │
└───────────────────────────────────────┬──────────────────────────────────────────────┘
                                        │ HTTPS（反向代理）+ JSON
┌───────────────────────────────────────▼──────────────────────────────────────────────┐
│ backend/server.py   路由分发 · 鉴权（会话 / API Key）· 限流 · 幂等 · 统一响应包        │
├──────────────────────────────────────────────────────────────────────────────────────┤
│ backend/mes.py      业务内核（纯函数，无 IO）：状态机 / 闸口 / OEE / 齐套 / CPK / 追溯  │
├──────────────────────────────────────────────────────────────────────────────────────┤
│ backend/db.py       建表与连接（WAL）        backend/seed.py  确定性演示数据            │
├──────────────────────────────────────────────────────────────────────────────────────┤
│ data/feichi.db      26 张表 / 索引；变更流 change_log 支撑增量同步                     │
└──────────────────────────────────────────────────────────────────────────────────────┘
                         │                                   │
                    Webhook（HMAC）                    增量同步（游标）
                         ▼                                   ▼
                 ERP / WMS / CRM 等外部系统（订阅事件、拉取变更）
```

**分层约束**：`mes.py` 只做纯函数计算（输入字典、输出字典），不碰数据库、不发网络请求，因此可以被单元测试 100% 覆盖；`server.py` 只做参数校验、事务与序列化；`db.py` 只管结构与连接。这条约束让"口径"只有一处实现，报表与页面不可能算错两套。

### 4.2 交互约定

- **一切以工单为中心**：详情弹层把闸口、工序、用料、检验、批次放在一屏，操作按钮按角色与闸口结果动态禁用并注明"缺 N 项"。
- **失败必须说清原因**：所有闸口校验失败返回"缺什么"，不使用"操作失败"这类模糊文案。
- **写操作二次确认**：取消工单、删除 Key / Webhook、吊销 Key 均需确认；取消工单必须填原因。
- **状态色统一**：草稿灰、已下达蓝、已开工金、已完工绿、已入库青、已关闭深绿、已取消红。

## 5 工单状态机与闸口

### 5.1 状态机

```
草稿 ──▶ 已下达 ──▶ 已开工 ──▶ 已完工 ──▶ 已入库 ──▶ 已关闭
  │        │          │          │          │
  └────────┴──────────┴──────────┴──────────┴──▶ 已取消（需填原因）
```

- **只能前进**：允许跨级推进（如已下达直接到已完工，但仍要满足全部闸口），不允许回退。
- **终态锁定**：已关闭、已取消不可再变更，任何写操作返回 400。
- **取消边界**：已入库之后不可取消（已产生批次与库存，需走报废或退货流程）。

### 5.2 五道闸口

| 目标状态 | 通过条件 | 设计意图 |
| --- | --- | --- |
| 已下达 | 计划数量 > 0；工艺路线已发布；BOM 已发布且有明细；物料齐套率 = 100% | 不让"缺料工单"下到现场 |
| 已开工 | 当前状态 ≥ 已下达；首件检验合格；已派工（有责任人）；工序涉及设备均可用 | 不让"没人干 / 设备坏 / 首件不合格"的工单开线 |
| 已完工 | 当前状态 ≥ 已开工；全部工序已完成报工；报工量 ≥ 计划量 | 不让"少做"的工单蒙混过关 |
| 已入库 | 当前状态 ≥ 已完工；完工检合格（含让步接收）；已生成批次 | 不让"未检"的成品进入库存 |
| 已关闭 | 当前状态 ≥ 已入库；无未处置不良 | 不让质量问题烂尾 |

闸口实现为一个纯函数 `wo_gate(target, ctx)`，返回缺失项清单（`[]` 表示可推进）。前端直接渲染清单，后端在推进时再次校验——**同一份规则既是提示也是拦截**。

### 5.3 报工闸口

报工是现场最频繁的操作，单独设三道校验：

1. **首件规则**：`fai_required = 1` 时，工单必须存在"首件 + 合格"的检验记录，否则拒绝报工。
2. **超报容差**：单工序累计报工量不得超过 `计划量 × (1 + over_report_tol)`（默认 5%）。
3. **状态约束**：草稿 / 已下达不可报工；已入库 / 已关闭 / 已取消不可报工。

## 6 核心算法与口径

> 所有公式集中在 `backend/mes.py`，前端不重复实现，接口返回即最终值。

### 6.1 产量口径（末工序法）

**问题**：一张工单有 5 道工序，每道工序都报 60 件，若按报工求和则产量为 300 件，重复计数 5 倍。

**解法**：产量只取每张工单**末道工序**的报工合计：

```sql
SELECT SUM(r.qty) FROM prod_reports r
JOIN (SELECT wo_no, MAX(seq) AS seq FROM prod_reports GROUP BY wo_no) m
  ON r.wo_no = m.wo_no AND r.seq = m.seq
```

同理，达成率的分母是"窗口内所有工单的计划量之和"，而不是"窗口内有产出的工单计划量"，避免因工单跨期造成达成率虚高（实测由 322% 回归到 69.5% 的合理区间）。

### 6.2 OEE

| 指标 | 公式 |
| --- | --- |
| 可用率 A | 运行分钟 ÷ 计划开机分钟（计划开机 − 停机） |
| 性能率 P | 理论节拍 × 产出 ÷ 运行分钟（上限 100%） |
| 质量率 Q | 良品数 ÷ 产出数 |
| OEE | A × P × Q |
| 等级 | OEE ≥ 目标（默认 0.85）→ 达标；≥ 目标 × 0.85 → 预警；否则未达标 |

设备日指标落在 `equip_metrics` 表（14 天），厂级 OEE 由全部设备指标按分钟与产量加权汇总。

### 6.3 设备可靠性

- **MTBF** = 累计运行时间 ÷ 故障次数
- **MTTR** = 累计停机时间 ÷ 故障次数
- **停机 TOP**：按停机原因分组汇总分钟数并计算占比，用于定位"最大损失源"。

### 6.4 生产与人力

| 指标 | 公式 | 说明 |
| --- | --- | --- |
| 工时达成率 | 标准工时 ÷ 实际工时 | > 100% 表示效率高于标准 |
| 产能负荷 | 工单标准工时 ÷ 产线可用产能 | 可用于排产冲突识别 |
| 节拍 | 可用时间 ÷ 客户需求 | 与产线实际节拍对比 |
| 产线平衡率 | 各工位工时之和 ÷ (瓶颈工时 × 工位数) | 越低越不均衡 |
| 瓶颈工序 | 单件工时最大的工序 | 排产与改善的第一目标 |

### 6.5 齐套率

对每一行用料：**可用量 = 现有库存 + 已发料（issued_qty）**；可用量 ≥ 需求量即为齐套。

- 按项齐套率 = 齐套项数 ÷ 总项数
- 按量齐套率 = Σmin(可用, 需求) ÷ Σ需求
- 缺口清单给出"物料、需求、可用、缺口"，直接可用于催料

### 6.6 质量指标

| 指标 | 公式 / 规则 |
| --- | --- |
| 良品率 | 良品 ÷ 产出（末工序口径） |
| PPM | 不良数 ÷ 产出 × 1,000,000 |
| 首件结论 | 零缺陷 → 合格；否则不合格（首件不允许让步） |
| 巡检结论 | 发现不良 → 异常，触发安灯与不良登记 |
| 完工检结论 | 0 不良 → 合格；不良率 ≤ `scrap_warn_rate`（默认 3%）→ 让步接收；否则退货 |
| Cpk | min((USL − μ), (μ − LSL)) ÷ (3σ)；≥ 1.67 充足 / ≥ 1.33 尚可 / ≥ 1.0 不足 / < 1.0 不足需改进 |
| 缺陷帕累托 | 按不良数量降序，累计占比 ≤ 80% 标记为关键少数 |

### 6.7 ABC 分类

按库存金额降序排列，判定使用"**加入本物料之前**的累计占比"：< 70% → A，< 90% → B，其余 → C。这样保证最大项必为 A 类，避免占比极高的单品被误判。

### 6.8 日期与班次

- 逾期：`planEnd < today` 且状态未到已完工 → 逾期；`planEnd − today ≤ 1 天` → 临期。
- 班次：S1 白班 08:00–16:00、S2 中班 16:00–24:00、S3 夜班 00:00–08:00；报工自动归班。

### 7.2 关键设计决策

- **单号规则**：`WO/RP/IQ/AD/MT/B + yyyyMMdd + -4 位流水`，人眼可读、可排序、可追溯日期；报工与检验单追加班次前缀（如 `RP101-03`）避免同一天多工单撞号。
- **工单工序冗余计划量**：`wo_operations.plan_qty` 在下达时按工单数量快照，工艺路线后续改版不影响在制工单——这是 MES 的硬要求。
- **批次父子链单独建表**：`batch_links(parent_batch, child_batch)` 支撑任意深度追溯，避免只存一列父批次导致链断。
- **变更流与业务表解耦**：`change_log` 只记录"对象类型 + 单号 + 动作 + 载荷摘要 + 时间"，外部系统按游标拉取，不暴露内部表结构。
- **索引**：工单（status、plan_end、material_code）、报工（wo_no、seq、reported_at）、检验（wo_no、type）、批次（material_code、wo_no）、变更流（id）等高频查询均有索引。

### 8.3 实现要点

## 10 集成设计

### 10.1 三条通道

| 通道 | 适用场景 | 机制 |
| --- | --- | --- |
| REST + API Key | 外部系统主动查询或写入（ERP 下发工单、WMS 取入库） | `X-Fc-Key: fck_xxx`，read/write scope，限流 240 次/分钟 |
| Webhook | 事件推送给外部（报工、入库、检验、不良、设备状态） | HMAC-SHA256 签名，失败退避重投 |
| 增量同步 | 批量对账（每日全量比对、断点续传） | `GET /api/sync/changes?since=<游标>&object=&limit=` |

### 10.2 Webhook 协议

- 请求头：`X-Fc-Event`（事件名）、`X-Fc-Timestamp`（秒级时间戳）、`X-Fc-Signature`（签名）、`X-Fc-Delivery`（投递 ID）。
- 签名算法：`HMAC-SHA256(secret, timestamp + "." + rawBody)`，十六进制小写。
- 验签方要求：校验时间戳偏差 ≤ 5 分钟（防重放）、签名比对用常量时间比较、按 `X-Fc-Delivery` 去重。
- 重投策略：失败后按 `30 × 2^n` 秒退避，最多 3 次；全部失败置终态，可在集成中心手动重投。
- 事件清单：`work_order.created`、`work_order.stage_changed`、`work_order.reported`、`work_order.stock_in`、`inspection.created`、`defect.created`、`defect.disposed`、`equipment.status_changed`、`maintenance.finished`、`andon.created`、`andon.closed`。

### 10.3 增量同步

- 每次业务写操作落一条 `change_log`（自增 ID 即游标）。
- 返回体：`{ changes: [...], cursor, hasMore, count }`；客户端保存 `cursor`，下次以 `since=cursor` 续拉。
- `payload` 只含对外字段摘要（单号、物料、数量、状态），不含内部自增主键，降低耦合。

### 10.4 外部 ID 映射

ERP 工单号、WMS 批次号与本地单号通过 `ext_mappings`（`obj_type + local_no + external_id + system`）双向绑定；`GET /api/integration/resolve?obj=work_order&externalId=ERP-WO-9001` 反查本地单号。

### 10.5 幂等与限流

- 写接口支持 `Idempotency-Key` 头，24 小时内同 Key 返回首次结果（`idem_keys` 表），避免网络重试造成重复工单。
- 单 IP 每分钟 240 次上限，超限返回 429，保护单机 SQLite 写锁。

## 12 前端设计

### 12.1 信息架构

六大分组 14 个页面：**生产运营**（驾驶舱、看板、排产、工单）、**主数据**（物料与 BOM）、**质量与追溯**（质量、追溯）、**设备管理**（设备、保养）、**库存与报表**（库存、报表）、**系统**（集成、设置、日志）。

### 12.2 实现要点

- **hash 路由**：`#orders?no=WO...`，刷新与分享均可用；页面注册表 `F.register(route, fn)` 惰性渲染。
- **零构建**：7 个 JS 文件按依赖顺序 `<script>` 引入，共享 `F` 命名空间；不引入任何框架，单页体积 < 180 KB。
- **可复用组件**：`F.table`（列定义 + 行点击 + 空态）、`F.dialog`（标题/主体/底栏按钮）、`F.chips`（状态筛选）、`F.progress`、`F.lineChart`、`F.barChart`、`F.ring`、`F.stageBars` 等，全部手写 SVG，无图表库。
- **看板大屏**：产线卡片 + 安灯表，30 秒自动刷新，字号与对比度适配车间电视。
- **权限驱动 UI**：`F.can(perm)` 控制按钮显隐，后端仍二次校验（前端只做体验，不承担安全）。

### 12.3 离线 DEMO

`demo/feichi-mes-demo.html` 是**单文件**演示版：内嵌确定性数据快照 + `fetch` 拦截器，在浏览器内存中实现全部写操作（建单、报工、推进、检验、不良处置、设备状态、保养完成、安灯、集成配置），并用 `sessionStorage` 保证页面重载后状态不丢。双击即用，无需后端与网络，用于客户演示与培训。

1. **功能**：14 个页面可用，工单六态全流程可走通，五道闸口按规则拦截并给出缺失项。

## 16 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 现场不报工或事后补报 | 数据失真、OEE 无意义 | 报工闸口 + 班次自动归集 + 看板公示到班组 |
| BOM / 工艺不准 | 齐套率与工时失真 | 上线前两轮主数据清洗，闸口强制"发布"才可用 |
| 单机 SQLite 写瓶颈 | 高峰期写入排队 | 写锁 + 限流 + 读走 WAL；规模超 300 人时迁 PostgreSQL（业务内核纯函数，迁移只改 db 层） |
| 与 ERP 编码不一致 | 对账困难 | 外部 ID 映射表 + 增量同步对账任务 |
| 设备未联网 | OEE 依赖人工 | 点检 + 报工 + 状态登记三源合成，二期接 OPC UA |
